# 設計が命

構造化しておかないと、後で別のもの同士が混ざり、原因を追えなくなる。責務や構造化の質が低い、または不足していると、その不足がそのまま負債になり、継続的に進化させる余地を狭める。

現実や現象と、それを扱うために人間が作る認知的な補助フレームワークは分ける。現実との一致、近似の精度、正解を出せるかは正誤判定で扱える。一方で、フレームワーク内部の粒度、責務、構造化のずれが積み重なる問題は、誤りではなく質や不足として扱い、改善対象にする。

AIもユーザーも、それぞれの認知モデルが行動しやすい環境を整えることを重視する。一般的な `この人がだめ` という評価は、その個の性能を引き出す前提、情報、道具、手順、フィードバック環境を整えないまま出ている場合がある。だから、人やAIを単体で評価する前に、まず環境づくりを改善対象に含める。

扱いが雑だと、大事なものが手からこぼれ落ちる。だから、対象、背景、関係性、距離、評価軸を雑にまとめず、必要な粒度で丁寧に扱う。

見方、観点、使う虫眼鏡や色眼鏡は一つに固定しない。複数の見方を使い、切り替えながら、対象、設計、評価、改善を進める。

そのため、情報は種類ごとに分ける。同じ情報が複数の分類に関わる場合も、分類ごとの役割、重要度、影響度、立ち位置を分けて扱う。

情報は個別の点だけで扱わず、構造化した単位として関連付けて把握する。構造単位では、目的、分類、責務、依存関係、評価軸、重要度、影響度を整理する。ただし、アプリやシステム内部の処理フローで、それらを常に一つの塊として運搬するという意味ではない。概念と関係性を明示しておくことで、後から別用途へ移す、比較する、拡張する、別の仕組みに接続する、といった選択肢が増える。

距離の取り方も大切にする。概念、設計、実装への組み込み方は、近づけすぎると混ざり、離しすぎると使えない。目的、責務、依存関係、実行時の扱いに合わせて、どこまで結びつけ、どこから分けるかを確認する。

型は、発散して試した後に収束してできるものとして扱う。発散の跡、経験、過去の正確な情報、ログが残っているから、後から抽象化し、汎用化し、必要に応じて修正できる。だから、判断や改善の材料になる情報は正確に残す。

世間一般の正解や、扱いやすいとされる体系だけを判断軸にしない。改善や進化の余地を常に探し、既存の選択肢がなければ作る。作ったものは、上手く動くまで小さく試し、測り、直す。ただし、独りよがりにならないよう、事実、効果、コスト、他者への伝わりやすさを確認しながら進める。

`独りよがりとは何か` も問いとして立てる。独りよがりかもしれないと感じた時は、決めつけず、対象、判断軸、根拠、影響、他者からの見え方を細かく分け、必要なら調査して確認する。こうした問いを大事にし、木の枝を伸ばすように、必要な観点を少しずつ増やして確かめる。頭の中の画像や3D的な構造イメージと、文章として書く内容も対応づけて扱う。頭の中にモデリングソフトがあるように、空間情報、前提、パラメータを変えながらシミュレーションする見方も尊重する。

評価するときは、既存の評価指標や評価体系を尊重する。そのうえで、それだけでは拾えないものも拾いにいく。定義済みの指標で見える範囲と、そこから漏れる違和感、未分類の失敗、まだ名前がない価値を分けて扱う。進化のきっかけは、こうした漏れを見つけにいくところから生まれる。だから、凝り固まった自分の見方をまず疑うところから始める。

この評価では、物理現象や理、既存の評価体系、独自に作る体系を混ぜない。数学や物理などの学問も、独自に作る評価軸やフローも、別の層として分けて扱う。そのうえで、何が何に対応しているか、どこで補完し合うかを見て、必要なら対象としているフロー自体も修正する。

評価時は、既存体系、独自体系、自分の仮説、人間の違和感、AIの出力を最初から上下づけしすぎず、まずフラットに並べて見る。その後、目的、根拠、実測に合わせて重みを付ける。

# はじめに

このリポジトリは、ハーネスを組むための実験的な作業情報を格納するためのリポジトリである。

- AIはどういう挙動をするのか、どういう入力に対してどのようなアウトプットを出すのか

- どういう制約や入力を与えればどのくらいの精度で動くのか、アウトプット目標とするチェックリストをどこまで満たすのか

- AI内部のアーキテクチャを分解するとどうなっているのか

などの項目を実際に調査実験するためのものである。

内容に関しては本 README も含め、適宜更新していく予定である。

## リポジトリの管理ルール

- 基本方針: 当リポジトリは実験場のため、原則として main ブランチのみで管理し、他のブランチは作成しません。

- 例外（別システムとの連携実験）:

    - システムを模擬的に連携させる場合は、**そのシステム名を表すブランチ（例: system-A など）**を適宜作成して進めて良い

    - ただし、セキュリティ上の理由から外部へのデプロイや公開は一切禁止

    - また、複雑な環境分離は不要なため、各システム用ブランチに対して develop や staging などの派生ブランチは作成しないこと（運用はシンプルに保つ）

- 作業時には必ず、ユーザーがこの会話で何を依頼したかを `internal_refs/chat_logs/YYYY-MM-DD.md` に記録する。既存ログは上書きせず、ユーザーの各メッセージごとに「依頼内容」と「AIが返した回答または実施した作業の約400字要約」を時系列で追記する。必須ルール化された指示・未完了事項があれば同じログに残し、会話単位で後から確認できる状態にする

- AIエージェントが必ず守る詳細ルールは `AGENTS.md` と `.agents/skills/chat-log-discipline/SKILL.md` にも記載し、README だけに依存しない

- AIが `優先度` や `おすすめ度` を出す場合、数字は `5` が高く `1` が低い。`優先度` は必ず「何の視点か」とセットで記載する

## 進め方の指針

- 人間の個の認知モデルとAIの認知モデルおよび推論同士が協業し、連携する。この場では、人間の個の認知モデルとAIの認知モデルのインスタンス同士が互いに認知の歪みや入出力の型のズレ、漏れと期待するアウトプットにどう影響したかを差分を相互確認しながら型・フォーマットを作成し、期待/指定品質以上のアウトプットをより短い時間、試行錯誤で生み出すためのガードレール付き作業環境を構築することを目的とする。

- 人間もAIも、自分たちの認識が正しいことを前提にしない。作業時は、次の3つを短く確認しながら進める。

    - Why: なぜやるのか。目的・背景・提供価値は何か

    - Real: 現状認識・観測・前提は実態と合っているか

    - Appropriate: 方法・コスト・品質・ステークホルダーを踏まえて適切か

- 必要に応じて、背景、現状、理想、今できる範囲、作業工程、アウトプット、ビジネス的視点、エンジニアリング・工学的視点を分けて確認する。観点漏れや認識のズレが見つかった場合は、その場で小さく修正する。

- 作業対象の責務と依存関係も、可能な範囲で先に洗い出す。必要に応じて、箇条書き、表、Mermaid 図などで可視化し、どの要素が何を担当し、何に依存しているかを確認しながら進める。

- 依存関係を見るときは、表面上の依存と、背景にある成立理由を分けて考える。責務や依存関係の管理では、まず実装・運用上の依存を扱う。そのうえで、必要に応じて「なぜその要素が存在してよいのか」「何がそれを成立させているのか」を考慮メモとして残す。例: 画面は API に依存しているが、API は画面や利用者価値を成立させるために存在している、という見方もできる。
