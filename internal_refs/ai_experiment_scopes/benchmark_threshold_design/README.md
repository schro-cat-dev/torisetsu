# ベンチマーク・閾値設計

## 目的

AI実験の評価軸、閾値、版、実測結果を分けて管理する。

## 結論

- ベンチマークは対象ごとに違う。
- 公開AIベンチマークは参考情報として扱うが、このリポジトリの伴走品質をそのまま決める基準にはしない。
- ユーザーが見ていること、考えていることに寄せる。ただし、方向性がずれていそうな場合は、理由を添えて別観点を提案する。

## 責務分離

| 場所 | 役割 |
|---|---|
| `targets/` | 対象ごとの評価軸と閾値 |
| `threshold_registry.md` | 現在使う閾値の一覧 |
| `version_ledger.md` | 閾値や評価軸を変えた履歴 |
| `experiments/` | 実測結果、比較結果、反省ログ |

## 公開ベンチマークの扱い

公開されているAIベンチマークは、統計的な傾向を見るための参考情報として扱う。

このリポジトリでは、次を優先する。

1. ユーザーの実作業で成果物が良くなったか。
2. ハーネスが抜け漏れを見つけられるようになったか。
3. 人間だけが気づくズレが減ったか。
4. 修正依頼の回数や時間が減ったか。
5. 別観点から見たリスクや盲点が残っていないか。

## ズレた時の扱い

AIが方向性に違和感を持った場合は、次の形で提示する。

```text
確認したいこと:
今の方向性は <理由> の点で少しズレている可能性があります。

根拠:
- <具体的な観測>
- <起きそうな問題>

提案:
- 案A: <ユーザーの方向性を維持して補強>
- 案B: <別観点から修正>
```

強く断定しすぎず、判断材料として出す。

## 追加時のルール

新しいベンチマークを作る時は、必ず次を分ける。

| 項目 | 内容 |
|---|---|
| 対象 | 何を測るか。例: TODOアプリレビュー、ハーネス品質 |
| 指標 | 何の数値を見るか |
| 閾値 | OK/注意/NGの境界 |
| 版 | いつ、どの理由で変えたか |
| 実測 | 実際の値 |
| 解釈 | その値をどう読むか |
| 残リスク | 数値だけでは見えないこと |
