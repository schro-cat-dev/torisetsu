# チームハーネス目標ドラフト

## 結論

チームハーネスは、技量差、前提差、職種差がある場面でも、設計事故やAI丸投げによる負債を増やさず、成果物へ安全に合流するために作る。

関連する詳細設計:

- [チーム一元化ハーネス 詳細設計ドラフト](../skill_orchestration_harness/team-centralized-harness-system-design.md)

## 目的

- 熟練者の判断や暗黙知を、シートや質問リストとして扱える形にする。
- 分からない人を責めず、必要な前提へ誘導する。
- AIがペアプロのように質問、確認、実装補助を行う。
- ツールの誤用、対象ズレ、権限ズレを早めに止める。
- 利用者ID、skill、タグ、品質評価を紐づけ、個人差とチーム標準を分けて扱う。
- 似た情報はグルーピングし、必要に応じて蒸留して短く使える形にする。
- ハーネス内部のナレッジを全部読ませず、一覧表から必要なものだけ選べるようにする。
- 利用者が裏側の仕組みを強く意識しなくても、推奨セットを選んで作業に入れるようにする。
- 暗黙知、チートシート、再利用できる実装module、品質チェック機構を、対象と観点に結びつけて扱う。

## 対象

- チーム開発。
- 職種が違う人同士の合流。
- DB設計、コア設計、権限設計など後戻りが重い領域。
- AIが支援する設計レビュー、実装レビュー、作業前確認。

## 大事にすること

| 項目 | 内容 |
|---|---|
| 提供価値 | チーム、利用者、事業、運用のどこに価値を出すかを最初に見る |
| 前提合わせ | 分からない領域でも、質問で必要な前提へ誘導する |
| 熟練者シート | 暗黙知を判断軸、質問、NG例、OK例として残す |
| 防御 | 対象、禁止事項、権限、手順、完了条件を先に確認する |
| 合流 | 成果物、証跡、レビュー結果を他者が読める形にする |
| 個人差 | 利用者ごとに合うskillや進め方が違う前提で扱う |
| 蒸留 | 似た情報を束ね、重複を減らし、大事な差分は残す |
| 採用アウトプット | 採用された成果物、修正過程、良くなった特徴を蓄積する |
| 選択窓口 | タスクやスコープごとに、使うナレッジだけ選ぶ |
| 類似性評価 | 本体情報とメタ情報セットを結びつけ、近い候補を出す |
| 2層検索 | 対象を絞ってから、観点や暗黙知を当てる |
| 再利用module | 汎用的な実装部品を蓄積し、条件が合う時だけ使う |
| 品質チェック機構 | 対象スコープだけを取り出して、OK/NGを確認する |
| config分離 | 具体ルールは外部入力へ出し、ツール本体を使い回す |

## 初期の成功条件

- 技量差があっても、設計前に危ないズレを見つけられる。
- AIが勝手に違う対象やスコープへ進まない。
- DB設計やコア設計で、権限、監査、運用、削除影響を確認できる。
- レビュー時に、どの判断軸でOK/NGにしたか分かる。
- タスク開始前に使うナレッジを選び、途中で必要なものだけ足せる。
- `今回DB設計` のような入力から推奨セットが出て、利用者は少数を選ぶだけで始められる。
- 対象、スコープ、処理IDで絞った後に、観点、タグ、暗黙知、チェックリストを当てられる。
- 汎用moduleと品質チェックが、同じ対象IDやscopeから辿れる。
- 新しい対象やルールを追加しても、ツール本体ではなく config、policy、scenario、contract の追加で対応できる。
- `flowId` と `typeModelRef` を混ぜず、`F2` は処理フロー、`X1-Y1-Y2` はデータ型定義モデル参照として扱える。
- `今回DB設計` のような入口から、本当に少ない操作で作業に入れるかを実測できる。
- 蓄積で速さ、品質、再現性、低コスト化が進むかを、仕様差分、Harness検出、人間検出、修正回数、所要時間で測れる。

## 採用アウトプットキャッシュの将来展望

良かったアウトプットは、最終採用された形だけを保存するのではなく、そこへ至る改善過程もセットで残す。

保存する観点:

- 採用された成果物。
- なぜ採用したか。
- 初期案から何が変わったか。
- どのフィードバックで良くなったか。
- どんな条件なら再利用できるか。
- そのまま使うと危ない条件は何か。

目的:

- 良い成果物の型を、感覚ではなく証跡つきで再利用する。
- 人とAIの協業で、どの改善が効いたかを後から確認できるようにする。
- チーム内で使える形に蒸留し、次のタスク開始時の迷いを減らす。

## ナレッジ選択窓口の将来展望

チーム版では、ハーネス内部のナレッジをすべてAIへ渡すと重くなる。

そのため、ユーザーの窓口として、一覧表から必要なナレッジだけを選ぶ仕組みを置く。

見る観点:

- タスク開始前に何を使うか。
- 今は何を使わないか。
- スコープが変わった時に何へ切り替えるか。
- 作業途中で何を追加するか。
- どのversionを使ったか。
- 使った結果、速度と品質がどう変わったか。

目的:

- 読み込む文脈を減らして速くする。
- 重要な判断軸は落とさず、品質を保つ。
- チーム、タスク、スコープごとに使うものを切り替えやすくする。
- 使い回し、改善、version管理をしやすくする。

## 推奨セットと類似性評価の将来展望

推奨セットは、用途別のスターターセットとして扱う。

テンプレに近いが、出力テンプレだけではない。checklist、skill、policy、sample、output-shape をまとめて、少ない選択で作業に入れるようにする。

例:

```text
今回DB設計
→ DB設計の基本セットが出る
→ 利用者が2つ選ぶ
→ 作業する
→ 必要なら audit-log-checklist を途中で1つ足す
```

類似性は、本体情報だけで見ない。本体情報に `tags / scope / taskType / quality / relation` などのメタ情報セットを結びつけ、それを評価して近さを見る。

目的:

- 似たナレッジを探しやすくする。
- 推奨セットや途中追加候補を出しやすくする。
- 本体情報と検索・評価用情報を混ぜずに管理する。
- 近いものを束ねても、大事な差分を消さない。

## ケース差分とインスタンス管理の将来展望

推奨セットのコアは、その場の都合で変えない。

ケースごとに違う前提、周辺状況、制約、追加/除外ナレッジを `execution instance` として分けて持つ。

目的:

- コアを守りながら、現場ごとの違いに合わせる。
- その場の調整を、すぐ全体ルールにしない。
- 複数回効いた調整だけ、base version の更新候補にする。
- 変更前/変更後、理由、影響範囲を追えるようにする。

## 次に作る候補

| 候補 | 優先度 | おすすめ度 | 背景 |
|---|---:|---:|---|
| チーム用設計前ゲート | 5 | 5 | 後戻りが重い設計事故を減らすため |
| 熟練者判断シート | 5 | 5 | 暗黙知を質問と判断軸に変換するため |
| userIdとskillの紐づけ | 5 | 5 | 個人差がある前提で、合うskillを出すため |
| タグ台帳と既存タグ確認 | 5 | 5 | 似たタグの乱立を防ぎ、探しやすくするため |
| グルーピングと蒸留 | 4 | 5 | 情報量を減らし、使える形に洗練するため |
| 採用アウトプットキャッシュ | 4 | 5 | 良かった成果物の特徴と改善過程を再利用するため |
| ナレッジ選択窓口 | 5 | 5 | 全部読ませず、速度と品質を両立するため |
| 推奨セットと類似性評価 | 5 | 5 | 少ない操作で必要候補を出し、途中追加もしやすくするため |
| ケース差分とインスタンス管理 | 5 | 5 | コアを守りながら、状況差分だけ調整するため |
| 2層検索と情報管理 | 5 | 5 | 関係ない情報を混ぜず、必要な観点だけ当てるため |
| 汎用module台帳 | 4 | 5 | 使い回せる実装を毎回作り直さないため |
| 品質チェック機構のscope連携 | 5 | 5 | 必要な範囲だけ取り出して品質保証するため |
| ツール本体とconfig分離 | 5 | 5 | 蓄積するほど速さ、品質、再現性、低コスト化に効くため |
| ツール誤用防止チェック | 4 | 5 | 対象外操作や権限ズレを止めるため |
| 合流用レビュー出力型 | 4 | 4 | 他者が読みやすく、引き継ぎやすくするため |
