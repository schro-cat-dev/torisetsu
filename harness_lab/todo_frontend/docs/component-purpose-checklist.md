## 2. コンポーネント別チェック

### 2.1 `TodoPage`

- 目的:
  - TODO 機能全体の親として、画面、状態、API イベントをつなぐ。
- 背景:
  - 小さい UI 部品が API を直接叩くと、処理の流れが追いにくくなる。
- 定性的効果:
  - 状態とイベントの入口が分かりやすくなる。
  - 画面全体の責任範囲を確認しやすくなる。
- 定量条件:
  - 子コンポーネントは `TodoPage` から props を受け取る。
  - API 通信は `TodoPage` ではなく `useTodos` に集約する。
  - 画面ルートは `/todos`、`/todos/new`、`/todos/completed`、`/todos/:todoId`、`/todos/:todoId/edit` を扱う。
- 完了条件:
  - [x] `TodoPage` が主要 UI をすべて配置している。
  - [x] `useTodos` を経由して API と接続している。
  - [ ] UI の責任が増えすぎたら分割判断を行う。

### 2.2 `TodoHeader`

- 目的:
  - 画面名、新規作成、完了済み一覧への導線を示す。
- 背景:
  - ユーザーが今どの画面にいて、主要操作へどう進むかをすぐ把握するため。
  - `Quality Harness` のような内部成果物名は、TODO管理の利用者UIには不要。
- 定性的効果:
  - 画面の現在地が分かる。
  - 一覧件数は一覧側へ寄せることで、ヘッダーの責務を軽くする。
  - 利用者の作業に関係ない文言が減る。
- 定量条件:
  - 新規作成導線を 1 つ表示する。
  - 完了済み一覧への導線を 1 つ表示する。
  - `/todos/new` では `一覧へ戻る` 導線を表示しない。
  - `Quality Harness` を画面に表示しない。
- 完了条件:
  - [x] `/todos/new` への導線がある。
  - [x] `/todos/completed` への導線がある。
  - [x] `/todos/new` が実際に作成モーダルへ自然につながる。
  - [x] 内部成果物名を利用者UIから外している。

### 2.3 `TodoCategoryBar`

- 目的:
  - 分類の選択、追加、色の見分けを一覧の上で行えるようにする。
- 背景:
  - 分類はTODOを探すための主要な切り口なので、検索入力の中に埋めるより見える位置に置く方が分かりやすい。
  - 画面幅が狭い時は、分類が増えても横スクロールで選べる必要がある。
- 定性的効果:
  - `すべて / プライベート / 仕事 / 日常 / 追加分類` をすぐ切り替えられる。
  - 分類色で、一覧の中の区別がしやすくなる。
- 定量条件:
  - `すべて` チップを 1 つ持つ。
  - `categories.json` から読み込んだ分類チップを表示する。
  - チップ領域は横スクロールできる。
  - 分類追加フォームで `name` と `color` を入力できる。
  - デフォルト分類は `locked: true` のまま変更しない。
- 完了条件:
  - [x] 分類チップを表示できる。
  - [x] 分類を追加できる。
  - [x] 分類色を選べる。
  - [x] 追加した分類で絞り込める。

### 2.4 `TodoCreateForm`

- 目的:
  - TODO の作成と編集入力を受け付ける。
- 背景:
  - 作成フォームと編集フォームで入力項目が同じため、同じ UI を使うと重複を減らせる。
- 定性的効果:
  - 入力、検証、保存の流れを 1 か所で確認できる。
  - 作成と編集で操作感をそろえられる。
- 定量条件:
  - `title` は必須。
  - `categoryId` は必須。
  - `title` は 80 文字以内。
  - `description` は 400 文字以内。
  - field meta から必須/任意、label、文字数上限を参照する。
  - `title` は `必須` badge を表示する。
  - `categoryId` は `必須` badge を表示する。
  - `description`、`priority`、`dueDate` は `任意` badge を表示する。
  - `title` は `現在文字数 / 80文字` を表示する。
  - `description` は `現在文字数 / 400文字` を表示する。
  - 分類は `categories.json` から読み込んだ一覧を表示する。
  - 新しい分類を追加できる。
  - デフォルト分類は `locked: true` として保存する。
  - 保存中は submit button を disabled にする。
  - 文字数超過中は submit button を disabled にする。
  - `label` と `input` を `htmlFor` / `id` でつなぐ。
- 完了条件:
  - [x] 作成フォームとして使える。
  - [x] 編集フォームとして使える。
  - [x] 入力エラーを表示できる。
  - [x] 必須/任意と文字数を表示できる。
  - [x] 必須/任意と文字数を field meta から参照している。
  - [ ] 作成用と編集用を同じコンポーネントにする判断が本当に適切か見直す。

### 2.5 `TodoToolbar`

- 目的:
  - TODO 一覧の検索、状態絞り込み、並び替えを操作する。
- 背景:
  - 一覧件数が増えたとき、探す・絞る・順番を変える操作が必要になる。
- 定性的効果:
  - TODO を探しやすくなる。
  - 表示条件が UI として明確になる。
- 定量条件:
  - 検索入力を 1 つ持つ。
  - 状態フィルターを通常一覧で 3 種類持つ: `all / todo / doing`。
  - 分類フィルターは `TodoCategoryBar` に分ける。
  - 並び順を 4 種類持つ: `createdDesc / dueAsc / priorityDesc / priorityDueAsc`。
  - 通常UIには再読み込みボタンを置かない。失敗時の `もう一度試す` に寄せる。
- 完了条件:
  - [x] 検索できる。
  - [x] 状態で絞り込める。
  - [x] 分類で絞り込める。
  - [x] 並び替えできる。
  - [x] 重要度が高く、期限が近い順で並び替えできる。
  - [x] 通常UIから再読み込みボタンを外している。
  - [ ] 表示条件を URL query に持たせるべきか判断する。

### 2.6 `TodoListSection`

- 目的:
  - 一覧領域の状態を出し分ける。
- 背景:
  - loading、error、empty、list が混ざると、一覧 UI の責任が曖昧になる。
- 定性的効果:
  - 一覧表示の状態を追いやすい。
  - 失敗時や 0 件時の体験を確認しやすい。
- 定量条件:
  - `isLoading` が true なら loading 表示。
  - `errorMessage` があるなら error 表示。
  - `todos.length === 0` なら empty 表示。
  - それ以外は `TodoList` を表示。
  - 一覧件数 `visibleCount / totalCount` を表示する。
- 完了条件:
  - [x] loading 表示がある。
  - [x] error 表示がある。
  - [x] empty 表示がある。
  - [x] list 表示がある。
  - [x] 件数が一覧領域内に表示される。
  - [ ] API mock で各状態を画面確認する。

### 2.7 `TodoList`

- 目的:
  - TODO 配列を 1 件ずつ `TodoListItem` に渡す。
- 背景:
  - 配列処理と 1 件表示を分けると、責任が小さくなる。
- 定性的効果:
  - 一覧の描画構造が読みやすい。
  - `TodoListItem` の見た目変更がしやすい。
- 定量条件:
  - `todos.map` で `TodoListItem` を作る。
  - `key` は `todo.id` を使う。
- 完了条件:
  - [x] `TodoListItem` を繰り返し表示する。
  - [ ] ページングや仮想リストが必要になったら見直す。

### 2.8 `TodoListItem`

- 目的:
  - TODO 1 件の内容と操作を表示する。
- 背景:
  - ユーザーは一覧上で、完了、詳細、編集、削除を素早く行いたい。
  - 詳細はカード本文クリックで開閉できる方が、右側ボタンより自然に扱える。
- 定性的効果:
  - 1 件ごとの状態と操作が見える。
  - 危険操作である削除を一覧から実行できる。
  - 詳細は行内トグル、編集はモーダルに分けるため、表示の役割が分かる。
- 定量条件:
  - タイトルを表示する。
  - 説明の短い要約を一覧に表示する。
  - 状態 badge を表示する。
  - 優先度 badge を表示する。
  - 分類 badge を表示する。
  - 期限 badge を表示する。
  - 操作は通常TODOで `編集 / 削除` の 2 つ。
  - 完了済みTODOでは編集を出さず、右側操作は `削除` だけにする。
  - 完了済みTODOの詳細も、カード本文クリックで開閉する。
  - 完了切替 checkbox を 1 つ持つ。
  - カード本文クリックで詳細を開閉する。
  - 右側に `詳細 / 閉じる` ボタンを出さない。
  - checkbox、編集、削除は詳細トグルへ伝播させない。
- 完了条件:
  - [x] TODO 1 件を表示できる。
  - [x] 完了切替イベントを親へ渡す。
  - [x] カード本文クリックで詳細を開閉する。
  - [x] checkbox以外のクリックで完了にならない。
  - [x] 削除前に確認を出す。
  - [x] 詳細は行内トグルで表示する。
  - [x] 編集はモーダルで表示する。
  - [ ] 削除確認が `window.confirm` で十分か見直す。

### 2.9 `TodoDetailPanel`

- 目的:
  - 選択した TODO の詳細表示をカード内で持つ。
- 背景:
  - 一覧だけでは、説明、期限、更新日時を落ち着いて確認しにくい。
  - 詳細が右上など遠い場所に出ると、どのTODOの情報か分かりにくい。
  - 右側の詳細/閉じるボタンを置くと操作が重複するため、カード本文クリックで開閉する。
- 定性的効果:
  - 選択中 TODO の情報をまとめて確認できる。
  - 一覧の文脈を保ったまま詳細を確認できる。
  - もう一度カード本文を押すと閉じられる。
- 定量条件:
  - `detail` mode では詳細表示。
  - 編集は `TodoPage` が別モーダルとして `TodoCreateForm` を表示する。
  - TODO が存在しない場合は未検出表示。
  - 詳細は対象 `TodoListItem` の中に表示する。
- 完了条件:
  - [x] 詳細表示できる。
  - [x] 編集フォームへ遷移できる。
  - [x] 存在しない TODO の表示がある。
  - [x] 詳細が対象カードの中で開閉する。
  - [ ] `TodoCreateForm` 再利用で責任が重くなっていないか見直す。

### 2.10 `CompletedTodosView`

- 目的:
  - 完了したTODOを、通常一覧とは別に確認する。
- 背景:
  - 完了済みが通常一覧に混ざると、これからやるTODOが見にくくなる。
  - 完了日時の新しい順で見られると、直近の作業履歴として確認しやすい。
- 定性的効果:
  - 未完了と完了済みの責務が分かれる。
  - 完了した順番を後から追える。
- 定量条件:
  - `/todos/completed` では `status === "done"` のTODOだけ表示する。
  - `completedAt` が新しい順に並べる。
  - 通常一覧では `done` を表示しない。
- 完了条件:
  - [x] 完了TODOが通常一覧から外れる。
  - [x] 完了TODOが完了済み一覧に出る。
  - [x] 完了済み一覧が `completedAt` の新しい順になる。
