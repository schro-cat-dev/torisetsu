# UIコンポーネント目的・効果チェックリスト

このファイルは、各 UI コンポーネントが「何のために必要か」を確認するための管理ドキュメントです。

優先度とおすすめ度は 5 が高い。

- [x] 背景を書く。
- [x] 定性的な効果を書く。
- [x] 定量的な条件を書く。
- [x] 完了条件を書く。
- [ ] 実ブラウザで、定量条件を目視または自動テストで確認する。

## 2. コンポーネント別チェック

### 2.1 `TodoPage`

- 目的:
  - TODO 機能全体の親として、画面、状態、API イベントをつなぐ。
- 背景:
  - 小さい UI 部品が API を直接叩くと、処理の流れが追いにくくなる。
- 定性的効果:
  - 状態とイベントの入口が分かりやすくなる。
  - 画面全体の責任範囲を確認しやすくなる。
- 定量条件:
  - 子コンポーネントは `TodoPage` から props を受け取る。
  - API 通信は `TodoPage` ではなく `useTodos` に集約する。
  - 画面ルートは `/todos`、`/todos/:todoId`、`/todos/:todoId/edit` を扱う。
- 完了条件:
  - [x] `TodoPage` が主要 UI をすべて配置している。
  - [x] `useTodos` を経由して API と接続している。
  - [ ] UI の責任が増えすぎたら分割判断を行う。

### 2.2 `TodoHeader`

- 目的:
  - 画面名、表示件数、新規作成導線を示す。
- 背景:
  - ユーザーが今どの画面にいて、何件見えているかをすぐ把握するため。
- 定性的効果:
  - 画面の現在地が分かる。
  - 検索や絞り込み後の件数変化が分かる。
- 定量条件:
  - `visibleCount / totalCount` を表示する。
  - 新規作成導線を 1 つ表示する。
- 完了条件:
  - [x] 件数が表示される。
  - [x] `/todos/new` への導線がある。
  - [ ] `/todos/new` が実際に作成フォームへ自然につながるか目視確認する。

### 2.3 `TodoCreateForm`

- 目的:
  - TODO の作成と編集入力を受け付ける。
- 背景:
  - 作成フォームと編集フォームで入力項目が同じため、同じ UI を使うと重複を減らせる。
- 定性的効果:
  - 入力、検証、保存の流れを 1 か所で確認できる。
  - 作成と編集で操作感をそろえられる。
- 定量条件:
  - `title` は必須。
  - `title` は 80 文字以内。
  - `description` は 400 文字以内。
  - 保存中は submit button を disabled にする。
  - `label` と `input` を `htmlFor` / `id` でつなぐ。
- 完了条件:
  - [x] 作成フォームとして使える。
  - [x] 編集フォームとして使える。
  - [x] 入力エラーを表示できる。
  - [ ] 作成用と編集用を同じコンポーネントにする判断が本当に適切か見直す。

### 2.4 `TodoToolbar`

- 目的:
  - TODO 一覧の検索、絞り込み、並び替えを操作する。
- 背景:
  - 一覧件数が増えたとき、探す・絞る・順番を変える操作が必要になる。
- 定性的効果:
  - TODO を探しやすくなる。
  - 表示条件が UI として明確になる。
- 定量条件:
  - 検索入力を 1 つ持つ。
  - 状態フィルターを 4 種類持つ: `all / todo / doing / done`。
  - 並び順を 3 種類持つ: `createdDesc / dueAsc / priorityDesc`。
  - 再読み込みボタンを 1 つ持つ。
- 完了条件:
  - [x] 検索できる。
  - [x] 状態で絞り込める。
  - [x] 並び替えできる。
  - [ ] 表示条件を URL query に持たせるべきか判断する。

### 2.5 `TodoListSection`

- 目的:
  - 一覧領域の状態を出し分ける。
- 背景:
  - loading、error、empty、list が混ざると、一覧 UI の責任が曖昧になる。
- 定性的効果:
  - 一覧表示の状態を追いやすい。
  - 失敗時や 0 件時の体験を確認しやすい。
- 定量条件:
  - `isLoading` が true なら loading 表示。
  - `errorMessage` があるなら error 表示。
  - `todos.length === 0` なら empty 表示。
  - それ以外は `TodoList` を表示。
- 完了条件:
  - [x] loading 表示がある。
  - [x] error 表示がある。
  - [x] empty 表示がある。
  - [x] list 表示がある。
  - [ ] API mock で各状態を画面確認する。

### 2.6 `TodoList`

- 目的:
  - TODO 配列を 1 件ずつ `TodoListItem` に渡す。
- 背景:
  - 配列処理と 1 件表示を分けると、責任が小さくなる。
- 定性的効果:
  - 一覧の描画構造が読みやすい。
  - `TodoListItem` の見た目変更がしやすい。
- 定量条件:
  - `todos.map` で `TodoListItem` を作る。
  - `key` は `todo.id` を使う。
- 完了条件:
  - [x] `TodoListItem` を繰り返し表示する。
  - [ ] ページングや仮想リストが必要になったら見直す。

### 2.7 `TodoListItem`

- 目的:
  - TODO 1 件の内容と操作を表示する。
- 背景:
  - ユーザーは一覧上で、完了、詳細、編集、削除を素早く行いたい。
- 定性的効果:
  - 1 件ごとの状態と操作が見える。
  - 危険操作である削除を一覧から実行できる。
- 定量条件:
  - タイトルを表示する。
  - 説明を表示する。
  - 状態 badge を表示する。
  - 優先度 badge を表示する。
  - 期限 badge を表示する。
  - 操作は `詳細 / 編集 / 削除` の 3 つ。
  - 完了切替 checkbox を 1 つ持つ。
- 完了条件:
  - [x] TODO 1 件を表示できる。
  - [x] 完了切替イベントを親へ渡す。
  - [x] 削除前に確認を出す。
  - [ ] 削除確認が `window.confirm` で十分か見直す。

### 2.8 `TodoDetailPanel`

- 目的:
  - 選択した TODO の詳細表示と編集導線を持つ。
- 背景:
  - 一覧だけでは、説明、期限、更新日時を落ち着いて確認しにくい。
- 定性的効果:
  - 選択中 TODO の情報をまとめて確認できる。
  - 編集へ進む導線を分けられる。
- 定量条件:
  - `detail` mode では詳細表示。
  - `edit` mode では `TodoCreateForm` を再利用。
  - TODO が存在しない場合は未検出表示。
- 完了条件:
  - [x] 詳細表示できる。
  - [x] 編集フォームへ切り替えられる。
  - [x] 存在しない TODO の表示がある。
  - [ ] `TodoCreateForm` 再利用で責任が重くなっていないか見直す。
