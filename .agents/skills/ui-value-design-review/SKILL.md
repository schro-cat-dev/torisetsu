# UI Value Design Review

この skill は、UI が利用者に価値を出しているかを確認するために使う。

## 1. 見る順番

1. `提供価値`: このUIは、利用者に何を楽にするか。
2. `ルートと変化`: ボタンやURL変更で、画面上の変化が分かるか。
3. `配置`: 関係する情報や操作が、近い場所にあるか。
4. `責務`: 一覧、詳細、作成、編集、内部情報が混ざっていないか。
5. `入力項目`: 必須、任意、文字数、エラーが入力欄の近くで分かるか。
6. `クリック範囲`: 見た目と実際に反応する範囲が一致しているか。
7. `重なり`: modal、背景、背面操作、z-index が自然に動くか。
8. `ノイズ`: 利用者の作業に関係ない文言や装飾がないか。
9. `ハーネス化`: 機械で確認できる条件に変換できるか。

## 2. 判断ルール

- 画面の見た目に出す情報は、利用者の作業に必要なものだけにする。
- `Quality Harness` のような内部成果物名は、利用者UIには出さない。必要なら docs や台帳で管理する。
- `新規作成` を押して URL が `/new` になるなら、画面も作成モードだと分かるように変える。
- 詳細表示は、対象アイテムとの関係が見える場所に置く。遠い右上に出すなら、強い理由が必要。
- 一覧と詳細に同じ情報を置く場合は、役割を分ける。例: 一覧は短い概要、詳細は全文。
- フォームの必須/任意/文字数は、表示だけで直書きしない。field meta などのデータから label、validation、文字数表示へ波及させる。
- クリック範囲は必ず確認する。`label` が広すぎる、親要素の `onClick` が子ボタンに伝播する、リンクとボタンが重なる、modalの背面がクリックを止める、の4つは先に疑う。
- checkbox は、タイトルやカード全体を不用意に包まない。完了クリックで行が消える仕様では、対象外クリックで完了しないことをE2Eに入れる。
- modal は、背景、白い面、重なり順、閉じる動作、同時表示の有無を確認する。詳細と編集が同時に開く、背景だけ出て中身が見えない、背面操作だけ止める状態はNG。
- 機能を足しすぎない。`必要 / おすすめ / 今はしない` に分ける。
- E2EやTDDで失敗した時は、テストを弱めて通すのではなく、`何を完了条件として確認すべきか` に合わせて対象を絞る。
- 例: 削除後の確認は `タイトル文字列が消えたか` ではなく、削除対象の `.todo-item` が0件になったかを見る。

## 3. フィードバックから設計へ変換する型

UIフィードバックを受けたら、すぐ個別修正だけにしない。次の形で、再利用できる判断材料へ変換する。

```text
ユーザーが大切にしていること:
- 例: ノイズを消す。操作対象の近くで分かる。詳細と編集を混ぜない。

設計パターン:
- 例: 作成/編集はmodal。詳細は対象カード内の行内toggle。

受けたフィードバック:
- 例: 詳細が右上に出ると、どのTODOの詳細か分かりにくい。

最終成果物:
- 例: カード本文クリックで詳細を開閉し、右側の詳細/閉じるボタンは消す。

UXの見方:
- 例: 操作距離、対象との近さ、クリック範囲、表示の安定性、不要な文言の少なさを見る。

ハーネス化:
- 例: カード本文クリックで詳細が開く。もう一度クリックで閉じる。checkbox以外で完了にならない。
```

## 4. 出力型

```text
結論:
<直す / 保留 / 追加確認>

事実:
- <コードや画面で確認できたこと>

修正方向:
- 必須度<1-5>: <何をどう直すか>

ハーネス化:
- <機械で確認できる条件>

未対応:
- <まだ残すこと>
```
