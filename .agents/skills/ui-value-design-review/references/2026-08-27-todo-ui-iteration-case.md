## 変換した設計判断

| 指摘 | 背景 | 修正方向 | ハーネス化 |
|---|---|---|---|
| 分類を探しにくい | selectだけだと一覧上の切り替えとして弱い | 検索バーの上に横スクロールの分類チップを置く | `分類: <name>` buttonをE2Eで確認 |
| 分類を追加したい | 作成時だけでなく、分類を先に作って選びたい | 分類バー内に追加UIを置く | 追加後にチップが表示されることを確認 |
| 色が欲しい | 分類の見分けやすさが上がる | `category.color` を追加し、badge/chipに反映 | contractで `#RRGGBB` を確認 |
| 必須/任意が遠い | 入力欄との対応が弱い | label横にbadgeを置く | `必須`/`任意`件数をE2E確認 |
| 文字数が遠い | 入力中の確認対象から離れる | 入力欄下に左寄せで置く | `n / 80文字` をE2E確認 |
| 作成領域がページ内に出る | 新規作成は一時操作に近い | モーダル化し、背景を薄暗くする | `dialog` とURL `/todos/new` を確認 |
| `一覧へ戻る` が不要 | モーダルならキャンセルで十分 | ヘッダーから消す | `一覧へ戻る` がないことを確認 |
| 完了後の行が残る | 完了済みと未完了の一覧責務が混ざる | 通常一覧から外し、`/todos/completed` で完了日時順に出す | `completedAt` と完了一覧を確認 |
| 件数がヘッダーにある | 件数は一覧状態であり、アプリ見出しではない | 一覧セクション内に移す | `表示件数` の領域を確認 |
| 詳細を見たい | 右側の詳細/閉じるボタンは重複しやすい | カード本文クリックで行内トグルにする | summary clickで開閉することをE2E確認 |
| 編集もモーダルにしたい | 新規作成と表示ルールを揃えたい | 編集フォームは `dialog` にする | `TODOを編集` dialogをE2E確認 |

## 再現ルール

- UIの違和感は、まず `対象 / 責務 / 配置 / 状態変化 / 操作距離 / 表示の安定性` に分ける。
- 「実装できるか」より先に「そのUIは何のためにあるか」を見る。
- 行やカードの高さが操作で変わる場合は、それが詳細確認として自然か、ただのレイアウト崩れかを分ける。
- 新規作成と編集はモーダル、詳細は行内トグルのように、表示形式を分ける場合は理由を書く。
- フィードバックを受けたら、`どう直したか` だけでなく、`なぜ変更したか` と `提供価値が何か` も残す。

## 提供価値

- 分類を探す、追加する、色で見分ける流れが短くなる。
- 入力欄と必須/任意、文字数の関係が近くなり、迷いが減る。
- 作成と編集はモーダル、詳細は行内トグルに分かれ、操作の重複が減る。
- 完了済みを別画面に分けることで、通常一覧は「これからやること」に集中できる。
- E2Eで確認できる条件に落とすことで、同じUI劣化を次回検知しやすくなる。
