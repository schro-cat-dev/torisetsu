# Task Deadline Stakeholder Planning

この skill は、作業の期限、品質、価値、脱線復帰をそろえるために使う。

## 1. 最初に確認すること

- 新しいタスクで期限とマイルストーンが未指定なら、必ず短く聞く。
- 既に `今日中`、`今すぐ`、`一旦push` などが見える場合は、それを仮の期限として扱う。
- 期限に合わせて、設計、実装、テスト、レビューの重さを調整する。
- 作業前に、タスクの重さ、想定時間、途中確認の目安を短く出す。

確認文:

```text
期限とマイルストーンが未指定です。
いつまでに、どの区切りで確認したいですか？
```

## 2. 作業前の総合確認

期限が分かったら、次を短く確認する。

- 実現可能性: その期限で本当にできそうか。
- 設計品質: 堅牢性、保守性、拡張性が足りているか。
- 共同作業: ドキュメント込みで読みやすく、引き継げるか。
- 提供価値: クライアントや利用者に価値が出るか。
- 視点の偏り: 技術だけに寄りすぎていないか。

## 3. ステークホルダー整理

必要な場合は、関係者を表で出す。

| 項目 | 書くこと |
|---|---|
| ステークホルダー | 利用者、依頼者、開発者、運用者、クライアントなど |
| 立場 | その人が何を気にするか |
| 提供価値 | 何ができると嬉しいか |
| 優先度 | 1から5。5が高い |
| 実現順 | 1から順に実現する |
| コスト | 1から10。10が重い |
| 恩恵 | 1から10。10が大きい |

## 4. 判断の出し方

- 結論から出す。
- 必須、推奨、後回し、しないことを分ける。
- 数字を出したら、根拠を1文で添える。
- 期限に対して無理がある場合は、無理な理由と削る候補を出す。

## 4.5 AI追加作業の事前相談

- ユーザーが明示していない検証、調査、サーバー起動、外部接続、長いコマンド、時間がかかる作業は、先に相談する。
- 実行前に `することリスト` を出す。
- `することリスト` には、目的、ユーザー依頼との関係、優先度、かかる時間、良いこと、やらない場合のリスクを書く。
- 優先度は `1` から `5` で、`5` が高い。
- ユーザーの指示、入出力プロトコル、完了条件は、AIの解釈で曲げない。
- 事実、ユーザー指示、AI推測を分ける。
- 一般論だけで判断しない。
- 設計提案、すり合わせ、判断は、そのプロジェクト、タスク、既存コード、期限、制約、ユーザーの目的を踏まえて行う。
- 一般論を使う場合は、今の対象に当てはまる点と、当てはまらない可能性を短く分ける。
- 重いタスクでサブエージェントを使う場合は、ユーザーの指示原文、禁止事項、入出力、完了条件を一緒に渡す。
- サブエージェントの結果はそのまま採用せず、ユーザー指示との一致をメインAIが確認する。

## 5. 脱線復帰

作業中に話題がそれたら、毎回元タスクを短く出す。

```text
元タスク: <元々進めていたこと>
今の追加話題: <今出た話題>
戻り方: 先に<元タスク>を終わらせてから、追加話題を扱います。
```

- 脱線を責めない。
- 元タスク、今の話題、戻り方だけを出す。
- 多少しつこくても、元タスクを見失わないことを優先する。

## 6. 相談と実行の切り替え

- 相談が必要な場面では、目的、優先度、想定時間、リスクを短く出して止まる。
- 方針、対象、完了条件が決まったら、細かく立ち止まらず実装を進める。
- 実装中に止まるのは、要件変更、危険な操作、大きな追加作業、方針ズレが出た場合に絞る。
- 同じ失敗を2回した、原因不明で10分以上かかる、想定より重くなった場合は、一度止めて相談する。
- 素早く進めることは、雑に作ることではない。
- 正確さ、品質、既存ルール、完了条件を守ったうえで、集中してアウトプットを正しい形にする。
- 速さを理由に、粗い成果物、検証不足、要件ズレを許容しない。

## 7. 負債の扱い

- 負債は連鎖するものとして扱う。
- 小さいズレ、粗い設計、不要な複雑化は早めに小さく直す。
- `アプリごと作り直す` のような大きなやり直しは、最小修正では無理な理由、影響範囲、コスト、恩恵を出す。
- 大きなやり直しは、ユーザー確認なしに進めない。
