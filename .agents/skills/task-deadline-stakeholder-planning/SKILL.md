# Task Deadline Stakeholder Planning

この skill は、作業の期限、品質、価値、脱線復帰をそろえるために使う。

## 1. 最初に確認すること

- 新しいタスクで期限とマイルストーンが未指定なら、必ず短く聞く。
- 既に `今日中`、`今すぐ`、`一旦push` などが見える場合は、それを仮の期限として扱う。
- 期限に合わせて、設計、実装、テスト、レビューの重さを調整する。

確認文:

```text
期限とマイルストーンが未指定です。
いつまでに、どの区切りで確認したいですか？
```

## 2. 作業前の総合確認

期限が分かったら、次を短く確認する。

- 実現可能性: その期限で本当にできそうか。
- 設計品質: 堅牢性、保守性、拡張性が足りているか。
- 共同作業: ドキュメント込みで読みやすく、引き継げるか。
- 提供価値: クライアントや利用者に価値が出るか。
- 視点の偏り: 技術だけに寄りすぎていないか。

## 3. ステークホルダー整理

必要な場合は、関係者を表で出す。

| 項目 | 書くこと |
|---|---|
| ステークホルダー | 利用者、依頼者、開発者、運用者、クライアントなど |
| 立場 | その人が何を気にするか |
| 提供価値 | 何ができると嬉しいか |
| 優先度 | 1から5。5が高い |
| 実現順 | 1から順に実現する |
| コスト | 1から10。10が重い |
| 恩恵 | 1から10。10が大きい |

## 4. 判断の出し方

- 結論から出す。
- 必須、推奨、後回し、しないことを分ける。
- 数字を出したら、根拠を1文で添える。
- 期限に対して無理がある場合は、無理な理由と削る候補を出す。

## 5. 脱線復帰

作業中に話題がそれたら、毎回元タスクを短く出す。

```text
元タスク: <元々進めていたこと>
今の追加話題: <今出た話題>
戻り方: 先に<元タスク>を終わらせてから、追加話題を扱います。
```

- 脱線を責めない。
- 元タスク、今の話題、戻り方だけを出す。
- 多少しつこくても、元タスクを見失わないことを優先する。
