# Alignment Gap Review Sample

## サンプル1: TODOアプリ設計

対象:

- TODO作成フォーム

確認:

| 種類 | 見ること | 判定 |
|---|---|---|
| 提供価値ズレ | 誰に何の価値を出すか | ユーザーが迷わずTODOを作れること |
| 目的ズレ | 何のためのフォームか | TODOを安全に作成するため |
| 粒度ズレ | どこまで分けるか | `TitleInput`、`SubmitButton`、`ValidationMessage` まで見る |
| 要素ズレ | 何を部品として見るか | 入力欄だけでなく、入力状態、保存中状態、API失敗も見る |
| 観点ズレ | どの見方で見るか | UI、状態管理、API、UX、保存可否で分ける |

レビュー結果:

```text
結論:
追加確認が必要。

ズレ:
- 種類: 要素ズレ
- 内容: 入力欄とボタンだけを要素として見ていて、保存中状態とAPI失敗時の表示が抜けている。
- 困ること: 実装後に保存失敗時の動きが曖昧になり、ユーザーが何をすればよいか分からない。
- 修正: `isSaving`、`errorMessage`、`ValidationMessage`、`SubmitButton disabled` を要素に追加する。

次の一手:
フォームの状態一覧を作り、各状態で表示するUIを1行ずつ書く。
```

## サンプル2: DB設計

対象:

- ユーザー情報テーブル

観点ズレの例:

```text
AIの見方:
ユーザー情報 = DBの列。id、name、email があればよい。

ユーザー側の見方:
ユーザー情報 = 権限、監査、個人情報、画面表示、削除時の影響、運用まで関係する情報。
```

レビュー結果:

```text
結論:
観点ズレがある。

ズレ:
- 種類: 観点ズレ
- 内容: AIはDB項目の空間で見ているが、ユーザーは権限や監査まで含む情報空間で見ている。
- 困ること: `email` を保存できても、誰が見られるか、誰が変更できるか、削除時に何へ影響するかが未設計になる。
- 修正: DB列だけでなく、権限、監査ログ、保持期間、削除時の影響を確認項目に追加する。

次の一手:
`ユーザー情報` を `DB項目 / 権限 / 監査 / 画面 / 運用` に分けて設計表を作る。
```

## サンプル3: AI作業依頼

対象:

- README更新依頼

レビュー結果:

```text
結論:
対象ズレと完了条件ズレを先に止める。

ズレ:
- 種類: 対象ズレ
- 内容: READMEの文言調整だけなのに、AIがAGENTS.mdやskillまで広げようとしている。
- 困ること: 低確度な情報がルール化され、後続作業の前提に混ざる。
- 修正: 今回触る対象をREADMEだけに固定する。

次の一手:
dry-runとして、READMEのどの見出しに何を1文足すかだけ提示する。
```
