# Alignment Gap Review

この skill は、AIや人間の作業が期待からズレていないかを確認するために使う。

## 使い方

1. まず `提供価値ズレ` を見る。
2. 次に、目的、対象、前提、粒度、要素、観点を確認する。
3. 最後に、手順、権限、完了条件を確認する。
4. ズレがある場合は、`どこがズレたか`、`なぜ困るか`、`次に何を直すか` を短く出す。
5. 必要なら `references/sample-review.md` を読む。

## ズレ確認リスト

| 種類 | 確認すること | 例 |
|---|---|---|
| 提供価値ズレ | 誰に何の価値を出すかが合っているか | 開発者の作業効率を上げたいのに、利用者画面の装飾だけ作っている |
| 目的ズレ | 何のためにやるかが合っているか | 設計事故を減らしたいのに、単なるTODO作成だけしている |
| 対象ズレ | 何を扱うかが合っているか | READMEを直す話なのに、アプリ実装を始めている |
| 前提ズレ | 事実や状況の理解が合っているか | APIあり前提なのに、ローカル保存だけで設計している |
| 粒度ズレ | どの細かさで見るかが合っているか | UI全体でよい場面か、コンポーネント単位まで必要か |
| 要素ズレ | 何を部品として数えるかが合っているか | 入力欄とボタンだけ見て、状態管理やAPI連携を見落としている |
| 観点ズレ | どの見方で要件や要素を見ているかが合っているか | 同じユーザー情報を、DB項目としてだけ見るか、権限や監査まで含めて見るか |
| 手順ズレ | 進め方が合っているか | 先に設計ゲートを見るべきなのに、実装へ進んでいる |
| 権限ズレ | 触ってよい範囲が合っているか | 消してはいけないデータや履歴を変更しようとしている |
| 完了条件ズレ | 何ができたら終わりかが合っているか | 動けばOKと思ったが、証跡とレビュー表まで必要だった |

## 観点ズレの補足

観点ズレには、概念や情報を扱う空間が違うケースも含める。

ユーザーの言い回しに寄せると、`概念とか、情報とかを扱う空間が違う` ために、同じ言葉を使っていても見ている場所が違う状態。

例:

- AIは `ユーザー情報` をDBの列として見ている。
- ユーザーは `ユーザー情報` を、権限、監査、個人情報、画面表示、運用、削除時の影響まで含む情報空間として見ている。

この場合、AIは `DB項目としては足りています` と言えても、ユーザーが見ている空間では不足している。

## 出力フォーマット

```text
結論:
<ズレている / 概ね合っている / 追加確認が必要>

ズレ:
- 種類: <提供価値ズレなど>
- 内容: <何がズレているか>
- 困ること: <放置すると何が悪いか>
- 修正: <次に何を直すか>

次の一手:
<すぐ動ける行動>
```

## 注意

- 人間の違和感を、機械が直接検出できるものとして扱わない。
- 機械で見る場合は、判定条件へ変換してから扱う。
- 抽象語だけで終えず、必ず具体例を1つ出す。
- ユーザーの言い回しを勝手に別概念へ置き換えない。
