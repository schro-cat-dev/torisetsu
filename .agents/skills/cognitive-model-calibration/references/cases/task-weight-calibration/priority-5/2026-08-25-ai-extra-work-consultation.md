# 2026-08-25 AI extra work consultation

## ユーザーからのフィードバック

することが決まりきっている実装で、AIが何時間も試行錯誤して待たせることがある。
時間がかかる前に一旦相談してほしい。
ユーザーが明示していない検証や追加作業は、実行前に `することリスト` と、目的、優先度、背景、良いことを説明してほしい。
AIの勝手な推測と行動がボトルネックや負債になるため、必ず相談してほしい。

追加で、負債は連鎖するので、小さい段階で一つずつ丁寧に修正する必要がある。
ただし、細かく自信なさそうに何度も立ち止まるのも困る。
方針、対象、完了条件が決まったら、安心してパッと進めてほしい。
この `パッと進める` は雑に作るという意味ではなく、正確さ、品質、既存ルールを守ったうえで集中して正しいアウトプットを出すという意味。
一般論だけでなく、そのプロジェクトやタスクの前提を踏まえて、話、設計提案、すり合わせを行う必要がある。

## ケース整理

- 方向性: `task-weight-calibration`
- 視点: `協働コスト削減`
- 優先度: `5`
- おすすめ度: `5`
- 根拠: 勝手な追加作業と長時間化は、待ち時間、要件ズレ、技術負債を増やすため。

## 次回からの反映

- 作業前に、タスクの重さ、想定時間、途中確認の目安を短く出す。
- ユーザーが明示していない検証、調査、サーバー起動、外部接続、長いコマンドは、実行前に相談する。
- 相談時は、することリスト、目的、ユーザー依頼との関係、優先度、想定時間、良いこと、やらない場合のリスクを出す。
- 同じ失敗を2回した、原因不明で10分以上かかる、想定より重くなった場合は止まって相談する。
- 方針、対象、完了条件が決まった後は、細かく立ち止まらず実装を進める。
- 素早く進める場合も、正確さ、品質、既存ルール、完了条件は落とさない。
- 速さを理由に、粗い成果物、検証不足、要件ズレを許容しない。
- 一般論だけで話さず、プロジェクト、タスク、既存コード、期限、制約、ユーザー目的を踏まえて提案する。
- 負債は小さい段階で修正する。大きな作り直しは、最小修正では無理な理由を出してから相談する。
